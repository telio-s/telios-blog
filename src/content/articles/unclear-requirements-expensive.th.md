โปรเจกต์ Software ส่วนใหญ่ไม่ได้แพงขึ้นเพียงเพราะนักพัฒนาเขียนโค้ดช้า แต่มันแพงขึ้นเพราะเริ่มสร้างก่อนที่การตัดสินใจสำคัญจะชัดเจน

Requirement ที่คลุมเครืออาจฟังดูไม่เป็นอันตรายในตอนแรก เช่น "เราต้องการ dashboard" "ลูกค้าควรส่งคำขอบริการได้" หรือ "แอดมินอนุมัติ order ได้" ประโยคเหล่านี้เป็นจุดเริ่มต้นที่ดี แต่ยังไม่พอให้ทีมประเมิน สร้าง และตรวจงานได้อย่างน่าเชื่อถือ

ส่วนที่แพงจะปรากฏทีหลัง เมื่อ workflow มีข้อยกเว้น บทบาทหนึ่งต้องการสิทธิ์ที่ไม่เคยคุยกัน หน้าจอดูถูกต้องแต่ไม่ตรงกับวิธีที่พนักงานทำงานจริง ทีมจึงต้องตัดสินใจว่านี่คือ bug, requirement ที่ตกหล่น หรือ request ใหม่

Requirement ที่ดีไม่ใช่เอกสารยาวเพื่อความยาวของมันเอง แต่มันสร้างความเข้าใจร่วมกัน อธิบายเป้าหมายทางธุรกิจ บทบาทผู้ใช้ workflow กฎทางธุรกิจ และ acceptance criteria

เมื่อฝั่งธุรกิจและฝั่งเทคนิคสามารถอ้างอิงข้อตกลงเดียวกันได้ บทสนทนาจะนิ่งขึ้น การประเมินชัดขึ้น change request แยกแยะง่ายขึ้น และสิ่งที่ส่งมอบตรวจเทียบกับสิ่งที่เป็นรูปธรรมได้

ความชัดเจนนั่นเองคือจุดที่โปรเจกต์ประหยัดเงิน
